## 2. Programming lets you hand precise thinking to a machine
Status: taught

Most of you don't have any programming experience, and this is your first programming course. Some of you don't even know what the languages are, or how to use a computer. So I am going to start from there.

So, what is a program? We have to start with that, because this is a course about programming. As the title says, we want to convert a precise problem into a program; that is our objective. There are lots of problems in the world. We are not going to solve all of them, but at least we can solve those that can be done with programming.

What does a program have? It has some input. You take some input, the program processes it, and it gives out some output. That is how a program works. As soon as you can explain a problem clearly, to yourself or to others, you can usually turn it into a program.

Why do we need programming? We want to talk to the computer. What does the computer understand - what is the language of the computer? Everyone knows it is binary: bits, 0s and 1s. If you want to tell the computer "hi", how do you say it in 0s and 1s? Just saying a bunch of bits does not work. How does the computer know that this set of 0s and 1s means "h" and this other set means "i"? [A student answers: ASCII.] Yes - we will learn what a compiler is, what ASCII values are, and everything else.

Many of these things are basics and you may already have learned them in school, but there are also people who have not done any programming at all so far. So in this course we will always start from the very basics at the beginning of a lecture, and then, towards the end of the lecture, we will go as far as we can with whatever you have learned so far.

Programming is writing a set of precise instructions that the computer can understand. How does the computer understand them? It converts whatever you write into machine code, which is binary - 0s and 1s - and then the computer carries out those 0s and 1s. {+The converter is the compiler: it translates the C++ into machine code once, and the CPU then fetches and executes that machine code directly. Some languages instead run through an interpreter, a program that reads your code and acts on it line by line; that is not what `g++` does.+}

What we want is to build programs so that we can automate things. If you want to calculate the average of five things, you don't want to do it by hand every time: take five numbers, add them, divide by five. You can write a program and do it automatically as many times as you want. Whichever branch of engineering you are in, you can use a program to automate parts of your task, and once you automate some parts you can focus on the parts that cannot be automated, where you need the human touch.

We will learn how to write and compile a program, and which programming language we will use. In this course we will learn with C++.

How do you run a program? We have to start by turning on the computer; otherwise you cannot run anything. When you go to the lab, the first thing to do is turn on the computer. If the plug at the bottom of the desk is unplugged, you may have to go down, plug it in and turn on the switch. Then press the power button on the box under the desk - in the lab people call that box the CPU, {+though strictly the CPU is the processor chip inside it, and we will use the word in that strict sense from here on+}. Does everyone know what a CPU is? Then you sign in to the computer. Do you know how the GUI works? All of you have used phones, and phones are touch screens; computers are not, so you have to use the mouse to move around.

The second part is the important part. Most of you have used phones, but when you go to a computer with an unfamiliar operating system - say Ubuntu - how many of you know what a terminal is? You have to use the terminal to run your program, and I will show you how. First you need the window that has the file manager; you can download a program, double-click it and open it.

Now, about how to work. You want to write a program, but you start from a problem and then work towards the steps of the program. You want a representation of the problem, in some abstract way, inside the program, so that you can say what the output should be. In the first few labs at least, what I want you to do is figure out the shape of your program, so that you can say precisely what the output will be even before you run it. If you cannot execute the program by hand and tell me the output, then writing code and hoping it will run and give the correct output is not enough. You should be very clear about the program you are writing: solve the problem, verify that the output is correct, and then improve it.

If your program takes one minute to run, you can improve it to make it faster. Why does it take one minute - can you do it in one second? Why one second - can you do it in one millisecond? And if it takes one millisecond, can you do it in one nanosecond? At what scale does a computer run instructions - how fast does a computer run? When you buy a computer or a phone, the advertisements tell you the processor has so many gigahertz. What is a gigahertz? It is the frequency at which the clock of the CPU runs. So if a computer runs at one gigahertz, that is 10^9 clock cycles per second, and one cycle takes one nanosecond. If your program needs to copy A to B, how many operations is that? One operation, you would think. So if it is only one operation, why can't you do it in one nanosecond? {+Because a clock cycle is not the same as an operation. A single instruction can take several cycles, and a copy from A to B is really a load from memory followed by a store, which can wait tens of nanoseconds if the value is not already close to the processor.+}

Why can't I do it in one operation? Because there is always overhead, and that overhead is what we mostly want to optimise. The target is always to find the minimum work you need, so that your program runs as fast as that allows.

## 3. High-level languages hide the machine; low-level languages expose it
Status: taught

Programming languages are divided into a hierarchy. At the bottom there are low-level languages, which are machine code, and at the top there are high-level languages, which are the modern programming languages. A low-level language is just a set of binary instructions. Slightly above that, but still at the low level, you have assembly languages. Assembly languages tell each register precisely what to do: copy this register, copy something from A to B, move this value by one, shift this register by one. {+Assembly is a readable spelling of the same machine instructions - one assembly line is one machine instruction - so machine code and assembly are both low-level; it is not a tier of its own between machine code and C++.+} And there are high-level languages like C++ and Python, where you do things based on formulas. You have learned so many formulas in mathematics and physics; you can write those formulas in this language, and once you write a formula you can execute it again and again on different inputs, and that is how you get the outputs.

## 4. Each generation of languages moves work from you to the compiler
Status: taught

When did these programming languages start - who can tell me when the first computer was invented? Any history nerds here? What happened in World War II? [A student answers: Enigma.] Enigma, right - {+Enigma was the German cipher machine, and the machines built to break it, the Bombe and then Colossus, are among the ancestors of the computer+}. When spies were sending encrypted messages, you wanted to break the ciphers as fast as possible, so that people could work out what message was hidden in them; that is the kind of calculation that pushed people to build machines. Around the same time there is ENIAC, and then EDVAC and EDSAC, the first big mainframe machines. {+ENIAC was finished in 1945 and computed artillery firing tables; EDVAC and EDSAC came just after the war and were the first machines to hold their program in memory the way computers do today.+}

Those were the initial machines, and on them people wrote the bits themselves - ones and zeros - to give to the computer. {+On the very first ones, like ENIAC, that meant plugging cables and setting switches by hand.+} Then there was something called a punch card: you made holes in the card and put the card into the computer; the computer saw where the holes were, and ran a program accordingly. {+Each column of holes encoded one character or number of the program, so the card was a way of typing the program in, one symbol per column.+} We are not doing that; we have evolved from that level.

We now have high-level programming languages. {+The first of those came in the 1950s: FORTRAN, Lisp, ALGOL and COBOL let people write formulas instead of instructions.+} The one our course descends from is C, which came in the early 1970s, from Dennis Ritchie, {+as one portable language for writing systems that until then had to be rewritten for every machine+}; and then in the 80s and 90s the next generation came, with more abstraction layers: C++, Python and Java.

What is the difference between C and C++? [A student answers: Object-oriented programming.] Yes. What C++ added on top of C is classes - object-oriented programming - and that is what we are going to learn in this course as well; it will come in the second half of the semester, after the mid-semester exam. {+Object-oriented programming is one style of high-level design, not the definition of high-level: C is high-level without it, and the idea itself is older than C++ - it comes from Simula and Smalltalk.+}

The modern programming languages are Rust, Swift and Go. We will not learn those specifically, but the point is for you to have an idea of what they are. They exist because of memory safety: we will learn during the course what a buffer overflow is, {+writing past the end of the memory you own,+} and these languages are designed to avoid that class of bug. {+They do it in different ways. Rust makes the compiler prove, before the program runs, that memory is used correctly, unless you explicitly opt out. Go and Swift remove many of the same bugs by managing memory for you and checking array bounds, without the same compile-time proof.+}

## 6. A program is a precise set of instructions a computer can execute
Status: taught

That is why we give the inputs as named values, and why the output is observable too.

A program is a precise set of instructions that a computer can execute, and the sample C++ code we saw is one of those programs. The thing with programs is that they are deterministic. That is why everything has to be very precise.

A set of precise instructions like this is the algorithm. "Algorithm" can mean a lot of things, but an algorithm is a set of steps that you need to follow. A program is more precise than that. An algorithm can be vague: I could say, calculate the time as distance divided by speed - that is just the algorithm. When you are writing the code it is not just the algorithm; you have to write it precisely enough for the computer to understand it.

So, problem, then model. Then we have to represent - how do we want to represent the problem in the data of the program? Then we solve the problem we are given, which is applying the formula you already know. And then you verify. After you solve, the first thing you need to do is always verify. You write a program and you don't know what the output is; for a small set of inputs you can compute the output precisely, and then you verify whether your program is running correctly. ## 8. The CPU executes instructions while RAM holds active state
Status: taught

When I talked about the instructions: the instructions are executed in the CPU. What is the full form of CPU? Everyone knows it: the central processing unit, which processes the instructions. And RAM - what is the full form of RAM? Random access memory. Why is it called random access? Who is confident that they know?

[A student answers: Because it can be assigned at random places in the memory.] No. [Another student: Because it is not dedicated to any particular task, you can use it for anything.] That is part of the answer, but not exactly.

What random access means here is this. In your phone you have 4 GB, 8 GB, 16 GB of RAM, whatever it is. RAM is divided into blocks of memory, and each block is, say, 8 KB. These blocks are directly accessible: you only need one address to access each block. It is random access in the sense that you can access any block. Say you have 4 GB of RAM and you divide it into 8 KB pages - how many pages is that? {+4 GB is 2^32 bytes and an 8 KB page is 2^13 bytes, so that is 2^19 pages, about half a million. The 2^32 is the number of bytes: a 32-bit address names one byte, which is why a 32-bit address space is 4 GB in the first place.+} Every one of those addresses can be named directly, and that is why it is called random access. Accessing each page takes only a constant amount of time, so you can reach any point in this very big block of memory directly.

The random access memory holds all the instructions of the program, and it also holds the state of the program. What is the state of the program? It is all the variables, all the values, all the inputs you have given, and whatever has been computed so far. If your computation has five steps and you want the final output at the last step, you also have to store the intermediate computations. If your formula is a times b times c, you cannot multiply three things at once in the computer: you first multiply a with b, store the result, and then multiply that result with c. That is how the computer works - it does not multiply a times b times c at once. Each arithmetic operator takes two operands: if you do an addition, it is a plus b. There are only two parts to each operation. That is why you need to hold the intermediate states of the computation, and those are also stored in the RAM. {+This is how a C++ expression is broken up, not a law of the hardware: processors do have instructions that combine three values, such as a fused multiply-add. And the intermediate values normally sit in the processor's own registers first; RAM holds whatever does not fit there and the state that has to survive between steps.+}

Then comes abstraction, because you don't want all of this written out by hand; you want some level of abstraction. Say you want to compute the [gravitational force] between two objects with masses m1 and m2. You know the formula - what is it? [A student answers: G*m1*m2 / r^2.] How many operations are there? First you multiply G with m1; then you multiply that result with m2; then you multiply r with r; and then you divide the one quantity by the other. Four operations.

That is where abstraction helps you, instead of writing each of those four operations separately. If you are writing machine code you have to write each one separately: let G equal this, one line; let m1 equal this, another line; let some other variable equal G times m1, another instruction; and then that result times m2, another instruction. That is how you would write assembly code. We are not doing that - we are writing in modern languages, so you write the whole formula, G times m1 times m2 divided by r squared, and that's it. {+In C++ that is `(G * m1 * m2) / (r * r)`.+} That is all you need to write in a C++ program, and that is where abstraction comes into the picture.

## 15. Names and declarations make program state readable
Status: taught

We are writing in a high-level language and we want to name things, and that is where a variable comes in. A variable is like when you write in mathematics - suppose x equals something. Similarly, in programming you write: data type, variable name, equals something.

The first one here says integer, and the short form of integer is `int`. Then I say `attempts`: how many times do you want to attempt JEE? Two times. So you write `int attempts = 2`, or `attempts = 1`, something. That is an integer.

For every variable you need to consider which data type to assign, and there are several data types. Whenever we assign these values, the variables have names, and here we want names that we can understand later. That is the point of the names. ## 17. Verify the travel-time estimator
Status: taught

Then there was the code I showed you where you take the distance and the speed and estimate the number of hours you need to travel. Every time you have written such a code, you also need to take input and verify that your code works. Once you have verified it for small values, you can be sure you have not made a mistake in your code. So always verify for small values - and on top of that you should also verify the boundaries.

What is something you know that is impossible in mathematics? [A student: Divide by zero.] A number cannot be divided by 0. If you write a program that divides by 0, what will happen? There will be an error. There are different types of error, {+and this one is a run-time error: the compiler cannot see that the speed will be 0, so the program compiles and starts, and the problem appears only when the division is actually executed. For integers, dividing by 0 is undefined behaviour and the program normally crashes there. For `double`, as in the travel-time estimator, the machine follows the IEEE floating-point rules instead: `120 / 0.0` gives `inf` and `0 / 0.0` gives `nan`, and the program carries on and prints that. Either way you do not get the answer you wanted, which is why the boundary has to be checked.+}

When writing programs, the first thing you need to understand is that the program should stop. If the program does not stop, you don't get an output. To get the output of a program, the program has to stop.

How does division work? [A student: Repeated subtraction.] You can always write a program that repeatedly subtracts one number from another, and when the number becomes smaller than the other number you stop - that is how you figure out the quotient. So if you are subtracting 0, you are constantly subtracting 0: the value never decreases and your program runs forever. {+That is what would happen if you wrote division yourself as a loop, and it shows why a program must be guaranteed to stop. The built-in `/` does not work by repeated subtraction, so `x / 0` does not hang; it fails in the way described above.+}

That is where the trace and the boundary cases come into the picture; you always have to check the boundary cases.

Similarly, you have to think about the range of your variables. If you are taking Fahrenheit, what is the zero for Fahrenheit? 32. So you have to check whether the value someone enters is valid or not. If you are taking a temperature in Kelvin, you cannot have negative numbers - in Kelvin all the temperatures must be positive.
